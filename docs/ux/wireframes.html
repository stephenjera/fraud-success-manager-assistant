One thing to decide — the rail’s “Evaluate”. Frame 1 and 2 show an Evaluate button on a pinned insight. But the contract’s backtest is a rule verb (POST /v1/rules/{id}/backtest), not an insight verb — an insight has no metrics until a rule draft exists. Two coherent shapes, pick one before Frame 2 is built:

(a) Two-step, one button. “Evaluate” silently fires POST /v1/insights/{id}/draft-rule then POST /v1/rules/{id}/backtest → the rail shows the rule’s metrics. Simple UX; but a draft rule now exists behind a button the FSM read as “just evaluate.”
    (b) Explicit hand-off. The rail button is Draft rule (→ rule created); the rule then owns its own Evaluate (backtest) in the catalog/detail. Matches the state machine (insight → draft → backtested) exactly, no hidden writes.

Nothing in the contract blocks either — it’s a UI semantics call. Recommend (b): it makes the insight→rule→backtest line (ADR-0005 wall, one trigger per edge in rule-lifecycle.md) visible in the UI instead of tucked inside a button. No API change required for either; only the button label/handling differs.
